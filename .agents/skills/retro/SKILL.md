# Evidence-earned retrospective

Run a retrospective only when at least one observable trigger is present:

- the owner requests one;
- a substantive escape or incident occurred; or
- repeated evidence shows a shared cause across delivery or review events.

A single ordinary correction does not trigger a retro. Return an explicit no-retro decision with
the evidence when no trigger is earned; never turn session wind-down into routine ceremony.

## Classify and group the evidence

Pin the triggering evidence to stable references such as issue identifiers, revisions, review
rounds, failing diagnostics, and validation results. Label these evidence pins as measured,
inferred, or still unknown without copying sensitive review bodies or personal data.

Distinguish an incident from a pattern. A substantive escape or incident may earn immediate
correction because of its impact even without repetition. A pattern requires repeated evidence,
not several descriptions of one event. Group evidence by shared cause rather than by symptom,
person, tool, or reviewer. Reject blame and unsupported claims.

## Select and prove the correction

Choose the smallest enforceable mechanism that addresses the shared cause. Prefer, in order, a
test, validator rule, structural change, or canonical procedure correction. Reject routine
ceremony, blame, narrative-only lessons, and “be more careful” prose.

Before accepting the mechanism, specify and run its RED mutation so only the motivating defect is
introduced and the expected failure is observed. Then correct the defect and run the exact GREEN
validation command. Record sanitized commands, exits, and diagnostics. If either measured result
is absent, the mechanism remains unproved; do not infer it from the proposed text.

## Route durable outcomes

Return the trigger decision, incident-versus-pattern classification, evidence grouped by shared
cause, selected mechanism, RED mutation, GREEN validation command, and any residual uncertainty.
New follow-up work belongs only in Linear under the root's authority. Never create a repository
document, memory entry, chat note, or private list as a second queue. Repository memory is reserved
for an earned, evidence-backed lesson that is not already enforced by code, tests, Git history, an
ADR, or the canonical procedure.
